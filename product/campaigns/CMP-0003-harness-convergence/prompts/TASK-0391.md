# TASK-0391 Declare applicability per check member and define the not-applicable result

Role: Architect. Round R-0309, wave CTG-0391. Record: ADR-CHK-0005.
Tier: architect (resolve the host model from `models.tiers` in campaign.json). Effort: high. Time budget: 90 minutes.

## Steps

1. Read ADR-CHK-0005, law/policy/check-suites.json, and law/schemas/check-suites.schema.json.
2. Add applicability (self, adopter, or both) to every member in check-suites.json and
   require it in the schema; action-coverage is both, action-effects and cli-reference
   are self. Regenerate any materialized suite view the policy feeds.
3. Define the not-applicable result on docs/reference/cli/check-suites.md: member,
   detected repository kind, how the kind was identified, selected input source,
   reason, evidence; distinct from PASS, REVIEW, and execution error in JSON, human
   output, and aggregate status; never a substitute for a missing required adopter
   source, an invalid explicit path, or a policy error.
4. State on docs/adopters/install.md and docs/adopters/ci-economy.md which members
   apply to adopters and how to test the classification.

## Deliverables

- Every check member declares applicability self, adopter, or both; action-coverage is
  both, action-effects and cli-reference are self unless a package-owned input mode is
  declared; the schema rejects a member without a declaration.
- The reference defines the not-applicable result (member, detected repository kind,
  how the kind was identified, which input source was selected, reason, evidence),
  states that it is distinct from PASS, REVIEW, and execution error in machine JSON,
  human output, and aggregate status, and that missing required adopter sources,
  invalid explicit paths, and policy errors never become not-applicable (#187).
- The adopter pages say which members apply to adopters and how to test the
  classification.
